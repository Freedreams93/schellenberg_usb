# Changelog

## v1.0.4

* Fix a real bug in `async_stop_cover()`'s failure path, found during an independent line-by-line audit: when `control_blind()` failed to send the stop (serial disconnected, transmit blocked, etc.) and the blind had been moving, the method restored `_attr_is_opening`/`_attr_is_closing`/`_move_start_time`/`_move_start_position`/`_target_position` to their pre-stop values - on the reasoning that a stop that never reached the stick probably didn't stop the motor either - but never restarted the position-tracking task that those fields feed, since it had already been cancelled earlier in the same call. The entity was left reporting `is_opening`/`is_closing` forever with a position frozen at the instant of the failed stop, until some unrelated later command happened to start tracking again. `_start_position_tracking()` is now called again in this branch when the blind was previously moving. Covered by two new regression tests
* Fix a real design gap in calibration, found during the same audit: recalibrating an already-configured blind (typically just to remeasure travel times) unconditionally applied whatever status identity that run's frame capture happened to discover, silently overwriting an already-working, previously-confirmed status identity with a possibly-wrong new guess - RF noise, a neighboring blind's remote, or another blind sharing the same capture window can all produce a plausible-looking but incorrect "primary" identity. Recalibration now only applies a newly discovered status identity when none was already known, or when it confirms the exact identity that was already configured (comparing through the same normalization every other identity comparison in this integration uses, so a different case or padding still counts as a match); a *different* discovered identity is left discarded - logged, not silently applied - while an already-known one stays untouched. To deliberately replace an already-known status identity with a genuinely different one, clear it first via the manual edit step, which still allows fresh discovery on the next calibration. Covered by three new regression tests
* Fix a real, if narrow, ambiguity between `control_blind()` and `send_command()`'s busy/retry bookkeeping, found while investigating a low-confidence item from the same audit: `control_blind()` (open/close/stop) deliberately writes straight to the transport with no lock and no bookkeeping of its own (see the entry below), so the stick's `tE` (busy) replies - which carry no id saying which write they are about - were always attributed to whatever `send_command()`-tracked transmission (teach, pairing, raw RF payload, verify) happened to be pending, even when a `control_blind()` write for a completely unrelated blind had landed in the same narrow window while that command was still waiting on its own `t0`. The result was a spurious automatic retry of the pending command - harmless for most of them, but teach's own docstring already warns that repeating it outside the motor programming sequence can change the motor's rotation direction. Rather than guess which transmission a `tE` in that window actually belongs to (the protocol gives no way to tell), it is now treated as ambiguous and simply not retried; a later, unambiguous `tE` for the same still-pending command (no intervening `control_blind()` write since) is retried exactly as before. Covered by four new regression tests
* Remove the priority-stop bypass and the busy-retry cycle's involvement in blind movement entirely, after live testing against two real blinds (kitchen, bathroom) showed them still colliding on real hardware: the log showed `Transmit retry limit reached source=cover payload=ss189020000 attempts=3; abandoning and latching busy state` for an in-flight move at the same time as `Priority stop bypassing lock source=priority_stop ... result=written_no_lock_no_ack_wait` for one of the two automatic follow-up stops meant to help interrupt it - one blind stopped several seconds late, the other did not stop at its target position at all. Two narrower fixes were tried first and both still failed the identical real-hardware test: clearing a competing pending retry whenever a priority stop fired, then exempting blind moves from the busy-retry cycle so a `tE` after one could no longer start a retry in the first place. Neither addressed the actual design flaw underneath both symptoms: `control_blind()` (open/close/stop) and `send_priority_stop()` (stop only) were two different transmission paths that could both be writing to the stick's single RF transmitter at the same time, and a transmit lock plus busy-retry cycle - built to serialize and recover *confirmable* commands - was fighting a lock-bypass path that only existed because that same lock was in the way. This RF link never confirms delivery to the motor to begin with (the USB stick's `t1`/`t0`/`tE` responses report only its own transmitter state, never what the motor did), so there was nothing worth serializing or retrying for these three commands in the first place. `control_blind()` now sends open, close, and stop the exact same way: one direct, unlocked write, with no retry and no busy-latch participation, and `async_stop_cover()` calls it directly instead of a separate bypass path. `send_priority_stop()`, the two lock-bypassing follow-up stop frames, and `cancel_pending_retry()` are all removed. The normal transmit lock and busy-retry cycle are unchanged for every other command (teach/pairing, raw RF payload testing, Developer Tools verify) - only open/close/stop opt out, since those were the only commands ever affected by the collision. Also fixes a related log message that had gone stale partway through this change: a busy (`tE`) reply to a command with nothing pending to retry (now every blind move) logged "will retry in 100ms" regardless, even though nothing would be retried; it now logs that there is no pending command to retry instead
* Fix a real bug in the pairing flow surfaced by actually running the new test suite for the first time: the hybrid ("pair and test, then choose") workflow's post-test-motor menu called `async_show_menu(step_id="test_success", ...)` with no matching `async_step_test_success()` handler, so Home Assistant raised `UnknownStep` and the flow crashed as soon as a user reached that menu. Added the missing step, mirroring the existing `async_step_manual_next` pattern already used one menu earlier in the same flow
* Fix a real bug in the calibration wait-for-movement/wait-for-stop listeners: they scheduled the `asyncio.Event` that unblocks the flow via `loop.call_soon_threadsafe(...)`, which exists to wake the event loop from a *different* thread. This integration only ever emits the underlying device-event signal from the event-loop thread itself, so the extra thread-safe scheduling hop was unnecessary - harmless at the multi-second pace of a real motor, but it delayed the flow by one extra loop iteration, which is exactly what made the new calibration tests for this code path hang instead of completing deterministically. Now sets the event directly
* Follow-up test fix (found because the above alone wasn't enough to stop one calibration test from still timing out): the tests' own `asyncio.ensure_future()`-plus-a-fixed-count-of-`asyncio.sleep(0)` dance, used to drive the background flow task forward one step at a time between simulated device-event signals, was still fragile - the exact number of loop iterations needed between a signal and the flow task registering its *next* listener depends on internal implementation details (such as `asyncio.wait_for()`'s own task-wrapping of its argument) rather than being a fixed, countable number. This was first changed to give the background task a real, short settle time between signals instead of counting bare `sleep(0)` calls - which turned out to still be the same kind of guess (a flat delay is no more guaranteed to be "long enough" on every machine than a fixed iteration count is) and still wasn't reliable. The calibration tests now remove the guesswork entirely: they wrap `async_dispatcher_connect` (as imported into `options_flow_calibration.py`) with a spy that flips an `asyncio.Event` on every real call, and await that event - directly, with no fixed delay - before sending the next signal. Since `_wait_for_movement_start()`/`_wait_for_stop_event()` each register their listener synchronously, with no `await` in between creating it and subscribing, that event resolves at the exact instant the flow task is actually listening, whatever that took, with its own 5-second `pytest.fail()` (independent of, and more specific than, pytest-timeout's blunter whole-test signal timeout) if a registration never happens at all
* Second follow-up fix, believed at the time to be the actual root cause of the intermittent calibration hang the two bullets above were chasing, and corrected by the third follow-up fix below once that belief turned out to be only half right: the wait-for-movement/wait-for-stop listener was never decorated with Home Assistant's `@callback`, so Home Assistant classified it as `HassJobType.Executor` and ran it on a worker thread instead of the event loop (confirmed against Home Assistant's own `homeassistant/core.py` and `homeassistant/helpers/dispatcher.py` source). Its body sets the `asyncio.Event` that unblocks the flow directly, and `asyncio.Event.set()` is not thread-safe - it only reaches the event loop safely via `loop.call_soon_threadsafe()`, not the plain `loop.call_soon()` that a `Future.set_result()` uses internally. The fix two bullets up (dropping `loop.call_soon_threadsafe(...)` for a direct `.set()`, reasoned as an unnecessary hop since the *sender* is always on the event-loop thread) was correct about the sender and incomplete about the *listener*: without `@callback`, the listener itself still ran on a worker thread regardless of where the sender ran, which turned that "unnecessary hop" into a real, intermittent cross-thread race. Both listeners (`_wait_for_movement_start`, `_wait_for_stop_event`) were decorated `@callback` on the (reasonable, but as it turned out wrong) assumption that this alone would make Home Assistant run them inline on the event loop
* Third follow-up fix, and the actual, verified root cause: adding `@callback` above did not stop the hang, because it does not actually guarantee inline execution on this integration's pinned Home Assistant test version - a `pytest-timeout` thread-based stack dump of a genuinely reproduced hang (not a theory) caught Home Assistant's dispatcher still routing the `@callback`-decorated listener through `hass.loop.run_in_executor(...)`, onto a worker thread, exactly as before that decoration was added. From there the exact same cross-thread `asyncio.Event.set()` problem the previous bullet describes still applied: `RuntimeError: Non-thread-safe operation invoked on an event loop other than the current one`, raised inside a fire-and-forget background job Home Assistant only logs ("Future exception was never retrieved") and never surfaces to the flow's own `asyncio.wait_for()` - so the event was never actually set, and every wait silently ran to its own full timeout. `@callback` is left in place (still correct style for a fast, non-blocking listener), but the `.set()` calls now go through `self.flow.hass.loop.call_soon_threadsafe(...)` again - restoring exactly what the first follow-up fix above removed, this time for a confirmed reason rather than a plausible-sounding but incomplete one
* Fourth follow-up fix, found by simply re-running the now-passing suite a few more times locally: `test_recalibrating_persists_new_times_and_notifies_the_live_entity` failed intermittently with `assert len(signals) == 1` reading `0`, even though the failure message's own repr of that same list already showed the one correct entry - a race, not a data bug. The test's own throwaway `SIGNAL_CALIBRATION_COMPLETED` listener (`lambda *args: signals.append(args)`) is neither a coroutine nor decorated `@callback`, so - exactly like the production listeners above, before their fix - Home Assistant is free to invoke it on a worker thread; the flow call returning is no proof it already ran. The test now waits for the listener to actually fire (via its own thread-safely-set `asyncio.Event`, the same pattern `_spy_on_dispatcher_connect()` already uses for listener *registration*) instead of assuming delivery from the awaited call returning
* Fix one more instance of the same kind of test-only mocking mistake as the test-only-mistakes list further below, missed at the time because it never crashed - only warned: `tests/test_options_flow.py` monkeypatched both `check_serial_port` and the synchronous, `@callback`-style `hass.config_entries.async_schedule_reload()` with `AsyncMock`. Production code correctly never awaits `async_schedule_reload()` (it only schedules a background reload), so calling the `AsyncMock` without awaiting it silently created an unawaited coroutine on every run that actually exercised it - a `RuntimeWarning`, not a failing assertion, found by reading a fully green run's warnings section rather than by anything actually breaking. Both now use a plain `Mock`, matching every other spy in this file
* Fix a real bug found the first time v1.0.4x (see that release's own changelog) was actually run against a real Home Assistant instance rather than just read: `manifest.json`'s `"version"` key had a stray leading `v` (`"v1.0.4"`), which happened to still parse as a valid version and so went unnoticed here, but the same pattern applied to v1.0.4x's own `"v1.0.4x"` does not parse at all - Home Assistant's loader rejects it outright ("does not have a valid version key") and silently refuses to register the integration, which is why every test that actually drives a real config/options flow for either release could have failed with `UnknownHandler`/`IntegrationNotFound`. Dropped the leading `v` here too (`"1.0.4"`), genuinely matching `pyproject.toml`'s version now instead of only appearing to (see the "Sync pyproject.toml's version with manifest.json" entry below, which fixed the number but not this prefix)
* Fix a real bug in the cover platform's stop handling: `async_stop_cover()`'s own initiating stop transmission went through the normal locked `control_blind()` path, same as open/close - only the two automatic follow-up frames after it bypassed the transmit lock. A stop exists specifically to interrupt whatever is currently happening, including an open/close command still in flight, so it must never queue behind one; and a caller that deliberately sends two `cover.stop_cover` calls a second apart as its own extra insurance against a motor that never acknowledges RF delivery (the same reasoning this integration's own automatic follow-ups already use) needs *both* of those calls to bypass immediately, not just their respective automatic follow-ups. The initiating stop now uses the same bypassing `send_priority_stop()` transmission as the follow-ups. `async_open_cover()`/`async_close_cover()`, Developer Tools, teach, and the single, non-doubled auto-stop-at-target call in the position-tracking loop are all unaffected and keep using the normal locked `control_blind()` path exactly as before. (Superseded by the top entry in this section: real-hardware testing later showed this same bypass colliding with an in-flight open/close command's own busy-retry, so `send_priority_stop()` and the bypass it gave the initiating stop were removed again, along with the two follow-up frames)
* Remove `async_step_blind`, a dead subentry-flow entry point that could never actually run: Home Assistant only ever starts a *new* subentry flow via `context={"source": "user"}` (confirmed by this integration's own `strings.json`, whose `config_subentries.blind.initiate_flow` defines only a `user` and a `reconfigure` entry, never `blind`) - subentry-*type* dispatch happens through the `(entry_id, subentry_type)` handler tuple, not through the step name. The removed method's own docstring described Home Assistant calling `async_step_{subentry_type}()`, which isn't how subentry flows actually work; `async_step_user()`, already implemented right below it, is the real, only entry point
* Fix several test-only mistakes found by actually running the new test suite for the first time - none of these affected the shipped integration; they were bugs in the tests' own mocking, timing, or fixtures:
  - `check_serial_port` (a synchronous function, called through `hass.async_add_executor_job`) was monkeypatched with `async def`/`AsyncMock` in several config- and options-flow tests, which either crashes real `asyncio` outright or silently leaves an unawaited coroutine; these now patch it with a plain `Mock`/`def`
  - two Developer Tools tests for "set position" failed because they never registered the test blind as a "live" cover on the api first, so `manual_sync_position()` correctly refused it as unregistered; they now register it the way `cover.py`'s own `async_added_to_hass()` normally would
  - the "test open/close/stop" Developer Tools test sent three commands back to back with no simulated stick acknowledgement, so the second and third were correctly refused as "transmit is pending" by the same guard that stops a real user from clicking a second test button before the stick answers the first; it now simulates the stick's own `t0` acknowledgement between commands, the way real hardware would send it
  - the "teach motor" test asserted 3 RF writes where the real, correct sequence is 4 (`teach_motor()` itself is a two-phase transmit - `teach_60` then `finish_40` - followed by open and stop)
  - a test for the hybrid workflow's fallback to the manual form inspected the form's schema with an empty probe dict, which is invalid here since the open/close time fields intentionally have no default until they are actually known; it now supplies both before reading the unrelated device-ID default it was actually checking
  - `test_developer_tools_reset_stick` triggered a real (and correctly failing, since the test's serial port doesn't exist) reconnect attempt, which schedules a 5-second retry timer that then outlived the test as a "lingering timer" failure at teardown; the test now disconnects the test api at the end, the same way a normal integration unload would
* Add a README section with an example automation for triggering several blinds from one switch and staggering each one's start so they finish moving at close to the same time, since a single USB stick can only transmit one RF command at a time and this integration tracks position purely from the calibrated open/close travel time, not real position feedback
