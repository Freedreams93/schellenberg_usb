# Changelog

## v1.1.3

* Optimize cover position handling so the "open" button is available immediately after pairing and calibrating a blind that ends up physically closed, without needing a manual "close" press first. Pairing a new blind triggers a full hub reload (`__init__.py`'s `_on_entry_updated`, which fires on every subentry add), and that reload replaces `entry.runtime_data` with a brand-new `SchellenbergUsbApi`, clearing the in-memory fresh-calibration cache (`set_fresh_calibration_position`/`pop_fresh_calibration_position`) before the newly created `SchellenbergCover` entity reads it back. If that same blind_id/entity_id had been used by an earlier pairing of the same remote (the legacy-unique_id migration in `async_setup_entry`), the entity also inherited a `RestoreEntity` state from that earlier pairing episode. `cover.py`'s `async_added_to_hass()` now falls back to the persisted `CONF_INITIAL_POSITION` subentry field (which survives the reload intact) with the same override priority over restored state the in-memory cache already had - but only for a blind that is itself newly registered (`SchellenbergCover`'s new `is_newly_registered_entity` flag, computed once in `async_setup_entry` from whether the stable unique ID had ever been seen before). Every other, already-established blind on the same hub goes through this same reload whenever *any* blind is paired, removed, or recalibrated, and keeps trusting its own current restored state rather than reverting to its own, possibly years-old `CONF_INITIAL_POSITION`. Covered by a new `test_cover.py` case for the newly-registered override, plus three new `async_setup_entry` cases establishing when `is_newly_registered_entity` is, and is not, set.

* Optimize status-identity discovery during calibration (the "Pairing and calibrating device" flow) on a stick shared with several blinds and Gurtwickler, so a single ordinary calibration cycle resolves the right device even when an unrelated device coincidentally transmits more raw frames during the same capture window. Status-identity discovery (`identities.py`'s `summarize_status_discovery_frames`) previously picked whichever device transmitted the most recognized frames, with no way to tell a real response from coincidental noise. Frames are now also weighted by whether their command matches the direction actually being driven in the phase they arrived in (`"opening"`/`"closing"`/`"opening_endstop"`/`"closing_endstop"`, already captured by `api.py` but previously unused for this). Covered by new `test_identities.py` cases, including one proving the noisy-stick scenario above would pick a different device without this change.

* Optimize the same status-identity discovery for the separate "Add roller shutter from remote control" flow, which listens to the stick without commanding the blind itself and so cannot use the phase-based weighting above at all - that flow labels every frame of its capture the same constant way throughout, with no direction for a frame to agree or disagree with. That flow's own on-screen instructions already ask the person to press OPEN, STOP, CLOSE, STOP on their existing remote, so frames are now also weighted by how closely a device's recognized commands follow that exact order, letting a device actually being pressed as instructed outrank a noisier, unrelated device transmitting coincidentally during the same listening window. Covered by two new `test_identities.py` cases.

* Fix the calibration-start question ("Bevor Sie beginnen" / `calibration_close`) visibly pre-selecting "fully open" before the person had chosen anything - the same ambiguity v1.1.2's own changelog entry for this step was meant to remove (see below). `vol.Required("initial_state")` genuinely carries no default, but that entry's assumption - that Home Assistant's frontend cannot submit a required select with neither option chosen - held only for the schema itself, not for how its "list" (radio) rendering actually draws an unanswered required field: confirmed live, it visibly highlights the first configured option before anything is chosen, indistinguishable from a deliberate answer. A third, clearly-not-a-real-answer "unselected" placeholder (`options_flow_calibration.py`, `strings.json` and all four translated files) now occupies that highlighted first slot instead of "open"; submitting it, or anything other than an explicit "open"/"closed", reshows the same form with a new on-screen error instead of silently being treated as "closed". Covered by a new `test_options_flow_calibration.py` case submitting the placeholder and then a genuine choice.

* Fix the same pre-selection problem in the pairing wizard's short motor test (`test_motor`, `config_flow.py`'s `_test_direction_schema`), found immediately after the fix above - it is built the same way, on the same now-corrected assumption. Same treatment: a third "unselected" placeholder occupies the highlighted first slot instead of "open", and `async_step_test_motor` now rejects it, or anything other than an explicit "open"/"close", with a new on-screen error instead of raising or silently picking a direction. `strings.json` and all four translated files gained the same placeholder label and error message as the fix above. Covered by a new `test_config_flow.py` case submitting the placeholder and then a genuine choice.

* Optimize the serial connection's error handling to drop a dangling reference to a `serialx.SerialException` that this library never actually defines - a lost or failed connection already raises plain `OSError`/`TimeoutError`, which is now the only thing caught. Also raise the minimum `serialx` version in `manifest.json` from `1.10.0` to `1.11.0`, matching what Home Assistant Core itself currently requires.

* Optimize the pairing cleanup step (`_stop_pairing_mode()`) by removing a leftover fixed 2-second delay that ran after every successful pairing for no remaining purpose.

* Optimize RF command retry handling into an endless, serialized retry loop with no retry limit, so a stick reporting busy is retried for as long as it keeps happening instead of eventually giving up.

* Remove the "Add another shutter on this same channel" repeat-pairing choice that used to follow every successful `add_shutter_from_remote` pairing, found to be unsound rather than merely a convenience: it deliberately gave a second Home Assistant entity the exact same command device ID/channel as the first (only their `unique_id` differed), so commanding either entity always moved both - regardless of which cover entity was actually addressed. Removed from `config_flow.py`: the `_offer_repeat_pairing` flag (previously always set by `async_step_add_shutter_from_remote`), `_last_ready_blind_data`/`_last_ready_blind_title`, `_pairing_unique_id()` (every pairing path now always keeps the plain command device ID as its `unique_id`, matching `pair_device` and the "existing" path), `_finish_pairing_or_offer_repeat()` (replaced by the plain `_finish_pairing()` it already fell back to), `async_step_pairing_repeat_choice`, `async_step_finish_pairing`, and `async_step_pair_another_on_channel`. `add_shutter_from_remote` itself - teaching the stick onto an already-paired physical remote's channel for one new device, a short motor test, then a choice between full calibration and manual travel-time entry - is unaffected and remains available from the subentry's initial menu alongside `pair_device`; it now always finishes by creating its one subentry immediately, the same way `pair_device` already did, instead of offering to loop back and pair a second device sharing that identity. `strings.json` and all four translated files lost only the `pairing_repeat_choice` step and its menu-option entries; `add_shutter_from_remote`/`test_success`/`manual_times` keep their existing strings unchanged. In the test suite, `test_config_flow.py` lost the two tests that exercised only the repeat-pairing choice (`test_manual_times_to_discover_status_offers_repeat_then_finish_creates_entry`, `test_add_shutter_from_remote_pair_another_on_channel_adds_a_second_blind`); the former's remaining coverage - confirming that the `manual_times` branch reaches a real `CREATE_ENTRY` for a brand-new device, not just the `discover_status` form - is kept by a new `test_manual_times_to_discover_status_creates_entry_directly`.

## v1.1.2

* Fix the pairing wizard's short motor test (the "Test" button in `test_motor`) usually not moving the motor at all: its fixed 0.75s hold before sending the follow-up stop was shorter than a real RF transmission (measured on real hardware at roughly 1.1-1.2s end to end), so the stop could be written while the direction command was still transmitting and corrupt or collide with it. The hold now waits for the stick to actually finish transmitting the direction command (`api.py`'s new `wait_for_transmitter_idle()`) before starting the unchanged `TEST_COMMAND_DELAY` hold, so the stop is never sent into an already-busy transmitter. The same wait was added to the Developer Tools "teach & test" action, which has the identical pattern. Covered by an updated `test_config_flow.py` case for the wizard's own test, and by `test_pairing_subentry_flow.py`'s existing Developer Tools teach-and-test case, whose mock api now also awaits `wait_for_transmitter_idle()` correctly instead of raising past it.

* Fix the same short motor test always testing "open" for a brand-new, not-yet-calibrated device regardless of its actual position: if the shutter happened to already be fully open (or, symmetrically, fully closed on a retry), the test correctly had nowhere left to move and looked like a failed pairing for reasons that had nothing to do with pairing. If the first attempt reports no movement, the wizard now automatically retries once toward the opposite direction before falling back to the manual form, and explains why in the confirmation text. A second "didn't move" answer - on the retry itself - is trusted and still falls through to manual entry as before. Covered by a rewritten and a new `test_config_flow.py` case.

* Fix `set_cover_position` (the position slider in the UI, and the `cover.set_position` service) being unable to reliably reach positions roughly within the first 10-15% of travel from either end stop on a fast-travelling blind. The background tracking loop (`cover.py`'s `_async_position_update_loop`) only decided to stop once its elapsed-time estimate had already reached the requested target - by which point the stop command itself still needed to be transmitted and acted on, which (see the test-motor fix above) takes roughly 1.1-1.2s on real hardware, during which the blind kept moving under the already-issued open/close command. For a short enough move, that stop could also be written while the stick was still busy transmitting that same open/close command, and since `control_blind()` deliberately never retries a busy (`tE`) response - to keep a manual Stop press instant, see its own docstring - it was then silently lost rather than merely late, letting the blind run on to the full end stop instead of stopping anywhere near the intended target. The loop now waits for that open/close command's own transmission to finish before ever sending the follow-up stop, and triggers the stop that many percentage points of this move's own travel time early to compensate for the latency that transmission still needs - both scaled from one new, shared constant (`STOP_COMMAND_LATENCY_SECONDS`, 1.2s), so a fast blind and a slow blind are each compensated correctly. Explicit 0%/100% targets are unaffected: those already rely on the motor's own physical end-stop rather than a command sent from here. Covered by three new `test_cover.py` cases: the early trigger itself, the boundary it must not fire before, and that an end-stop target still skips both the wait and the stop.

* Fix a 2-minute pairing timeout permanently blocking every later pairing attempt instead of just that one. Both pairing entry points - "Pairing and calibrating device" and "Add roller shutter from remote control" - share one cleanup step after pairing ends (`api.py`'s `_stop_pairing_mode()`), which toggles pairing off by resending the same "sp" command used to enter it and only then considered the stick back in listening mode. That command is not an RF transmission and so never gets the t1/t0 reply the confirmation wait was actually listening for (unlike a real transmit command, see `send_command()`'s own `is_transmit` comment); on real hardware, leaving pairing mode measurably takes a few seconds, which could run past that wait's fixed timeout even though the stop command itself had already gone out successfully. When that happened, the stick's mode was left on "unknown" rather than "listening", which then made `_transmit_capability_block_reason()` reject every subsequent `pair_device_and_wait()` call outright - so reopening either pairing option immediately re-showed the same "pairing timed out" message again, before a new attempt to find a device could even begin, until Home Assistant was restarted or the stick reconnected. The successful "sp" write alone now decides the stick is back in listening mode, the same way `_enter_listening_mode()` already trusts a successful "hello" write with no ACK wait at all - so a slow-to-confirm exit from pairing mode no longer blocks the next attempt. Covered by two new `test_api.py` cases: `_stop_pairing_mode()` restoring listening mode on its own when the confirmation wait times out, and a full `pair_device_and_wait()` timeout followed by a second attempt that genuinely retries instead of being rejected outright.

* Finish the fix just above: `_stop_pairing_mode()` no longer waits for an idle confirmation at all. That wait could never reflect "sp" itself (see the fix above for why), only some unrelated, possibly stale idle flag, so once the stick's mode no longer depended on whether that wait timed out, the wait itself had nothing left to decide - just a chance to add up to its own timeout's worth of pointless delay before the stick visibly returned to listening mode. It now goes straight from a successful "sp" write to "listening", with no wait in between.

* Remove 14 `api.py` methods, and the protocol constants that only they used, found to have no caller anywhere in the integration, its tests, or `services.yaml` during a full audit of the codebase for unreachable code: `get_recent_raw_frames`, `remove_known_device`, `update_connection_status`, `led_blink`, `set_upper_endpoint`, `set_lower_endpoint`, `allow_pairing_on_device`, `manual_up`, `manual_down`, `echo_on`, `echo_off`, `enter_bootloader_mode`, `enter_initial_mode`, and `reboot_stick`. None of these were ever wired to a UI step, a service, or a test - `remove_known_device` was already fully superseded by the complete entry reload that already runs whenever a blind is removed, which rebuilds the same bookkeeping from scratch, and `update_connection_status`'s own docstring already called it a compatibility shim for callers that no longer exist. The write-only `_raw_received_frames` buffer that only `get_recent_raw_frames` ever read is removed with it. `CMD_ALLOW_PAIRING` and `CMD_PAIR` are kept, since `teach_motor()` still sends both. No behavior changes for anything reachable from the UI.

* Modernize `PLATFORMS` (`const.py`) to Home Assistant's `Platform` enum instead of three bare strings.

* Fix a freshly paired blind's starting position sometimes showing the wrong end immediately after a "Pair and calibrate" run - e.g. the "open" arrow disabled on a blind that had just finished calibrating closed - reported from testing a real device. The new entity has no chance to receive `SIGNAL_CALIBRATION_COMPLETED` the way an existing blind being recalibrated does, since it doesn't exist yet when calibration finishes; it instead falls back to whatever Home Assistant restored for its blind_id in `async_added_to_hass`, and a restored state was always trusted over the `CONF_INITIAL_POSITION` fallback added when choosing the calibration direction was introduced above.
