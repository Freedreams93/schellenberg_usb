# Changelog

## v1.1.0

* Add a clearly-named recommended pairing entry point, **Add a Shutter or Shutters from a Remote to Schellenberg-USB** (`add_shutter_from_remote`), and rename **Pair and calibrate** to **Learn from remote, skip test (legacy)** (unchanged behavior - still skips the movement test). The previous "Pair and test"/"Pair and calibrate" labels gave no hint of what either path actually did until you were already inside it. `add_shutter_from_remote` also now offers, right after a successful test, to pair another blind that shares the exact same remote channel - without repeating any of the pairing/naming/test steps for it. Each blind still gets its own generated unique ID rather than the shared RF identity itself, so two or more blinds sharing one remote channel never collide or overwrite each other's configuration
* Add a direction-aware, confirmation-gated movement test (`test_motor`): nothing is transmitted until the test is explicitly confirmed, and the direction is now chosen automatically from the device's last known position - closed drives it briefly open, open drives it briefly closed, defaulting to open when no position is known yet - instead of always testing the same direction regardless of where the device actually is. This is shared by every entry point that ever ran this particular movement test (`add_shutter_from_remote`'s hybrid workflow, `pair_device`-followed-by-manual-test, the manual-entry flow, and reconfigure's "test existing device"), since they already funneled into the same underlying step
* Make the entire configuration/options user interface device-generic instead of blind-specific: "Blind" became "Device" (and the matching word in German, Spanish, and French) everywhere it meant the generic controlled device rather than literally a roller-shutter blind - menu labels, step titles and descriptions, error/abort reasons, service and diagnostics text. This integration already worked with any Schellenberg RF receiver (electronic belt/strap winders, awning motors, and similar motorized devices, not just roller shutters); the wording now says so instead of implying blinds only
* Add a shared runtime-translation module (`runtime_translation_text.py`, originally written as `runtime_text.py` and renamed - including every internal function and constant name - before release) and wire it through `cover.py`, `switch.py`, `__init__.py`, and `options_flow_calibration.py`. Every previously hardcoded English UI string surfaced by those modules - cover open/close/stop failure messages, the LED switch's on/off failure messages, the `test_command` service's validation errors, both device "model" strings, and the calibration summary's fallback text - is now translated into German, Spanish, and French the same way `config_flow.py`'s own strings already were, rather than falling back to English regardless of the configured language. Translations deliberately avoid word-for-word literalism (the kind that previously produced the awkward German "Endegrund") in favor of natural phrasing in each language
* Replace `pyserial`/`pyserial-asyncio-fast` with `serialx==1.10.0`, the library Home Assistant Core itself has been migrating to since its 2026-04-27 developer announcement (older Core releases still ship `pyserial-asyncio-fast`/`pyserial`, but newer ones no longer carry them - Home Assistant Core's own `usb` component already requires this exact `serialx==1.10.0` version). `check_serial_port()` now opens the port through `serialx.serial_for_url()`, `connect()` opens the async connection through `serialx.create_serial_connection()`, and the connect-failure and config/options-flow error handling now catch `OSError`/`TimeoutError` alongside `serialx.SerialException` instead of `serial.SerialException`
* Fix `_last_transmit_source` never resetting: once a diagnostic-sourced transmission (Developer Tools, the `test_command` service) completed, every later, unrelated `t1`/`t0` from a completely different source kept being logged at that stale source's level instead of its own. A clean `t0` completion now resets it to `"internal"`, the same way a `busy_latched` stick that has plainly recovered is no longer shown as stuck (see next entry) - both are diagnostics-only; no command was ever blocked by this
* Fix `busy_latched` never self-clearing once latched: previously only a full disconnect/reconnect cleared a stick that diagnostics had marked "stuck busy" after exhausting its retries, even if the stick quietly recovered and went on to acknowledge later commands normally. A clean `t0` completion now clears the latch as well, so diagnostics stop reporting a stuck state that no longer reflects reality. This is diagnostics-only - a genuinely still-stuck stick latches again on its own next failed attempt, and no real command was ever blocked by the stale flag
* Add mock-test coverage for `cover.py`'s `async_open_cover()`/`async_close_cover()` - previously only `async_stop_cover()`'s success and failure paths were tested, leaving open/close completely unverified, including the regression risk of `_attr_is_opening`/`_attr_is_closing` sticking `True` after a failed command
* Add mock-test coverage for `switch.py`'s `async_turn_on()`/`async_turn_off()` - previously untested in either direction; only the reconnect-triggered hardware-restore path had tests
* Add mock-test coverage for the `test_command` service's third `ServiceValidationError` branch (`control_blind()` refusing to transmit) - the other two branches (entry not loaded, ambiguous entry selection) were already covered
* Add mock-test coverage for both `api.py` fixes above (`_last_transmit_source` resetting to `"internal"`, `busy_latched` self-healing on a `t0` with no disconnect in between) and strengthen the calibration summary's existing test to check the translated fields it fills in, not just the two numeric travel times
* Add dedicated `test_config_flow.py` coverage for the pairing menu's final shape: `add_shutter_from_remote`'s repeat-offer path (pairing a second blind that shares the exact same remote channel, with each blind still getting its own unique ID, never the shared command identity) alongside its plain single-blind path through to a real `CREATE_ENTRY`
* Add direct `test_api.py` unit coverage for three `api.py` methods that previously had none at all beyond incidental, indirect exercise through `test_config_flow.py`'s own higher-level tests: `teach_motor()` (success, blocked while disconnected, a failed first transmit, and the ACK-wait-timeout path that latches busy), `pair_device_and_wait()` (a full successful pairing captured from a synthetic unknown-transmitter frame, refusing a second concurrent pairing attempt, returning `None` when not transmit-capable, and timing out when nothing responds), and `send_raw_transmit()` (rejecting an invalid payload, refusing while disconnected, and a successful send that normalizes case)
* Restore `test_runtime_translation_text.py` (renamed from `test_translations.py`) and `test_pairing_subentry_flow.py`, both lost to an environment reset after they had already run successfully once; the two test runs they left behind (a full `uv run pytest` transcript and its tracebacks, plus a before/after coverage diff) were used to reconstruct their intent, exact expected wording, and which `config_flow.py` lines they exercised. `test_pairing_subentry_flow.py` now covers every Developer Tools menu action at the unit level - the three direct test commands, manual position sync (`set_position_open/closed/manual`), teach motor, send raw RF payload, discover status from the original remote (plus its confirmation step), and copy diagnostics - including paths the recovered tracebacks alone did not reveal, such as a command correctly blocked by `transmit_block_reason` and one correctly reported as failed when its API call returns `False`. Deliberately not duplicated here: the pairing/manual-entry/calibration workflow steps also reachable from this class, which stay covered through `test_config_flow.py`'s full-flow-manager tests instead of a second, unit-level pass over the same logic
* Add six `test_config_flow.py` cases found missing while auditing exactly that pairing/edit coverage: a brand-new device's pairing was never actually followed through to a real `CREATE_ENTRY` on the "manual_times"/discover-status branch (only the "calibration" branch and the reconfigure/Developer-Tools update-existing branch were); re-testing an already-configured blind and answering "it didn't move" fell through to its `edit` form untested; editing a blind's identities had no case for an invalid enum or for clearing a previously-discovered status identity by leaving both fields blank; the manual-entry flow's own "test_motor" menu choice (as opposed to "save_manual") had never been followed through to its `CREATE_ENTRY` either, even though it is a separate code path reached straight from `did_motor_move` with no return to that menu; and the short motor test's own `command_failed` error - shown when the stick reports the RF command itself could not be sent, distinct from the person saying the motor didn't move - had no test at all
* Remove one trivially-true, misleading assertion (`busy_latched is False` after a `t1` that had never set it `True` to begin with) that wrongly implied `t1` was responsible for clearing the latch, now that the real self-healing behavior has its own dedicated test
* Update the README: the quick-start section now also mentions `add_shutter_from_remote`'s repeat offer for a shutter sharing the same remote channel, and the "other setup methods" section describes the actual current menu (`add_shutter_from_remote`/`pair_device`/`manual`) instead of the superseded "Pair and test"/"Pair and calibrate" wording. A new "Multiple remotes" section under Position tracking separately clarifies that a motor can learn several remotes at the hardware level, but Home Assistant's own position tracking only follows the specific RF identities it has actually discovered via calibration or status discovery - a remote or channel it has never seen a recognized frame from will still move the device, just without Home Assistant noticing
* Add mock-test coverage for `cover.py`'s core runtime logic - the elapsed-time position estimate itself (`_update_position`), both ways the background tracking loop can reach a full 0%/100% end stop purely by elapsed time with no explicit target, the full-travel-resync gate that withholds that detection until a restored/resumed move has actually covered its whole configured travel time, the activity-event handler that starts/stops tracking and freezes the estimate on a STOPPED echo (including the invert-direction case and clamping a near-end-stop position to a clean 0/100), the position slider's routing logic (`async_set_cover_position`), manual position sync and calibration-completion handling, and restoring the last known position (from the current-position attribute, from a plain open/closed state, or defaulting to closed) plus the dispatcher-signal wiring that lets the activity-event handler receive anything at all. The stick has no return channel from the motor - this is the actual logic the "live" position shown while a blind is moving is built on, previously almost entirely untested (`cover.py` coverage: 44%). `async_setup_entry` (entity/device-registry creation and legacy-ID migration at startup) and `api.py`'s incoming-frame parser (which is what turns overheard remote activity into the events this logic reacts to) were not covered by this pass - infrastructure and wire-protocol parsing respectively, rather than the entity's own runtime behavior; both are closed instead by the three entries below
* Add direct `test_api.py` coverage for `connect()` - previously exercised only indirectly, and only on its exception branch, through Developer Tools' "Reset stick" test: the success path (opening the port, verifying the stick, entering listening mode, then fetching the hub ID), and the two failure branches that each reset state and schedule a reconnect instead of leaving the connection half-open (device verification failing, entering listening mode failing)
* Add direct `test_api.py` coverage for `_handle_message()`'s `"ss"` and `"RFTU_"` branches - the actual incoming-frame parser, previously only exercised end-to-end through `test_config_flow.py`/`test_cover.py`'s own tests, which fire the resulting dispatcher signal or resolved future directly and never feed the parser a real wire frame: recording a tracking frame and dispatching both the per-device and per-identity signals for a registered entity, skipping the per-identity signal for a frame from a device nothing has registered, resolving a pending pairing future from an unknown transmitter's frame instead of dispatching it as a normal status update, and resolving the stick-verification future from an `RFTU_` reply
* Add direct `test_cover.py` coverage for `async_setup_entry()` - previously completely untested, including by `test_config_flow.py`'s higher-level tests, which only ever exercise the config/options flow, never the cover platform's own setup: a saved blind's device-registry entry and entity are keyed on the subentry's own stable `unique_id`, never the raw RF identity used only to transmit; a subentry missing a usable command identity is silently skipped instead of crashing setup for every other blind; a pre-stable-ID entity's `schellenberg_<device_id>` unique_id is migrated onto the current format in place; and a non-hub entry or a hub with no saved blinds yet is left alone
* Add direct `test_switch.py` coverage for `switch.py`'s `async_setup_entry()` and the LED switch's restore-on-startup/reconnect wiring - previously untested: the hub subentry is correctly attached as the switch's `config_subentry_id`, a hub-less entry still creates the switch ungrouped, a restored `on` state pushes the LED on immediately when already connected, a restored state is kept but not pushed to hardware while still offline, no previous state at all defaults to off, and the dispatcher signal that detects a stick reconnect actually triggers the hardware-state restore
* Add direct `test_init.py` coverage for `async_setup_entry()`'s device-registry branches and firmware tracking - previously untested: a hub device somehow left on the wrong config subentry (for example after an interrupted migration) is reassigned back onto the hub subentry instead of staying stranded, and the hub device's reported firmware version is refreshed once the stick reports it, even though setup already created the device without one
* Add `test_config_flow.py` coverage for three manual-entry validation branches that previously had no test at all: an incomplete status identity (one of the two fields filled in, not both), a non-positive open or close travel time, and a malformed secondary status identities list
* Fix the manual-entry and reconfigure/edit steps' travel-time fields rejecting a non-positive value with a raw, untranslated schema error that aborted the entire config/options flow, instead of the translated `invalid_travel_time` field error their own validation code was already written to show: each field's `NumberSelector` had its own `min=0.1`, which Home Assistant enforces before calling the step handler at all, so that validation code could never actually run. Found by the test added just above, which a selector-level `min` made genuinely unreachable until now. The one other, unrelated use of the same selector (`async_step_manual_times`, shown between a successful paired-command test and status discovery) keeps its own `min=0.1` unchanged, since that step has no such follow-up validation of its own to hand off to
* Add `test_runtime_translation_text.py` coverage for `runtime_translation_text.py`'s own public functions directly, not just their effect as exercised indirectly through other modules' tests: parity checks that German, Spanish, and French each define exactly the same keys as the English reference table (catching a missing or extra translation before it reaches users), plus dedicated tests for every function's individual branches, including at least one non-English language for each
* Fix two remaining literal-German occurrences of "Endegrund" in `translations/de.json` (the calibration-complete and developer-tools step descriptions) that had survived the `runtime_translation_text.py` translation work above - corrected to "Abbruchgrund", matching the natural phrasing already used everywhere else in the project for the same concept
* Audit the whole integration for missing or inadequate docstrings and fill the gaps found: entirely undocumented public setup/teardown functions (`cover.py`'s and `__init__.py`'s `async_setup_entry()`, plus `__init__.py`'s `async_setup()`, `async_unload_entry()`, `_async_backfill_blind_ids()`, the `test_command` service's call handler, its two voluptuous field validators, and its subentry-reload comparison helpers), and docstrings that only echoed their function's name without saying what it actually does (the incoming-message parser `_handle_message()` in `api.py`, the LED switch's reconnect handler in `switch.py`, the calibration flow's two event-wait closures, and its `calibration_complete` step, whose docstring previously described only its confirmation-form branch and not its much larger persist-or-offer-repeat-pairing branch)

* Fix calibration's movement-wait steps (`_wait_for_movement_start()`/`_wait_for_stop_event()` in `options_flow_calibration.py`) never receiving a confirming signal for a device whose status (receive) identity differs from its command (pairing) identity - a protocol-documented possibility (see README's "Advanced protocol notes": command and status identity can differ for one physical device). Both listeners previously subscribed only to `SIGNAL_DEVICE_EVENT_{command_device_id}`, which `api.py`'s `_handle_message()` only ever sends for a frame carrying that exact identity, so such a device's real status frames never matched and calibration always timed out even though the motor genuinely moved - independent of which pairing entry point was used, and reproducible with any real device whose two identities differ (first reported against an electronic belt/strap winder). Fixed by also broadcasting a new, capture-wide `SIGNAL_DEVICE_EVENT_CAPTURE` signal from `_handle_message()` for every `"ss"` frame received while a status-frame capture window is open (the same window calibration already opens for its own, unrelated status-identity discovery), and having both wait steps additionally listen on it as a fallback
* Restructure the "Add device" pairing menu: **Pair a shutter and calibrate it** (`pair_device`, previously labelled "Learn from remote, skip test (legacy)") is now the first menu option instead of the last, with its "(legacy)" labelling dropped in all four languages - the calibration fix above applies to it exactly as it does to the two recommended paths, so it is no longer a lesser, deprecated fallback. Remove the standalone **Add manually** menu entry and its dedicated top-level tests. Update the README's "Other setup methods" section to match
* Add `test_options_flow_calibration.py`/`test_api.py` regression coverage for the calibration root-cause fix above: a full open/close calibration run that only ever receives its movement-start/stop confirmations on the capture-wide signal, tagged with a device id different from the one being calibrated, still reaches `calibration_complete` instead of timing out; and `_handle_message()` only broadcasts `SIGNAL_DEVICE_EVENT_CAPTURE` while a status-frame capture window is actually open, never otherwise
* Drop the word "directly"/"direkt" from `pair_device`'s menu label and step title in all four languages - it added nothing and read as implying the other two options were somehow indirect
* Reword `add_shutter_from_remote`'s description to name every supported device type explicitly (an RF shutter motor, an electronic belt/strap winder, or an awning motor), not just shutters, matching the integration's actual device-generic scope
* Shorten both pairing-option menu labels and step titles (`pair_device`, `add_shutter_from_remote`) in all five language files - the previous long titles wrapped to two lines and were visually clipped by the Home Assistant mobile app's fixed-height header
* Rewrite the `test_motor` step's description in plain, beginner-friendly language, replacing the dense technical wording (arrow notation, "Befehlsidentität") with complete sentences

## v1.0.4

* Fix `pyproject.toml`: `pytest`/`uv run pytest` could not import `custom_components` (`ModuleNotFoundError: No module named 'custom_components'`) because `tests/` intentionally has no `__init__.py`, so pytest's default import mode only ever added `tests/` itself to `sys.path`, never the repository root. This affected every test run through the bare `pytest` entry point - including the "Run pytest" step in `build-test.yaml` and the local pre-commit hook, both of which call `uv run pytest` rather than `python -m pytest` (which would have masked it). Fixed by adding `pythonpath = ["."]` to `[tool.pytest.ini_options]`
* Fix the retry limit for "stick busy" (`tE`) answers: it counted over the whole connection and was never reset, so the fourth busy answer since the connection was opened was not retried and blocked Developer tools. It now starts over when the stick accepts a transmission
* Fix Developer tools refusing commands with `transmit is pending for payload sr` right after connecting: plain requests such as the device ID query are no longer remembered as pending RF transmissions
* Update the README: the `Transmit error - stick busy` log filter is no longer needed, and the two fixes are described in the troubleshooting section
* Correct the coverage settings in `pyproject.toml`: `if TYPE_CHECKING:` blocks are excluded and the `main()` pattern no longer hides the hub config flow
* Add a priority-stop bypass: every stop command is now followed by two extra, lock-bypassing stop frames one second apart, since a Schellenberg motor never confirms it actually received an RF stop frame
* Fix a crash in the `test_command` service when a configured Schellenberg USB entry exists but was never loaded (`runtime_data` is only set once an entry is actually set up, so the service loop now tolerates entries that don't have it yet)
* Fix a race in the "stick busy" retry logic where Home Assistant's eager task scheduling could run a retry to completion before it was assigned to `_retry_task`, leaving a stale, already-finished task there instead of `None`
* Add forward-compatible handling for Home Assistant 2026.10's deprecation of `DeviceEntry.config_entries`/`.config_entries_subentries`/`.primary_config_entry` in favor of singular `config_entry_id`/`config_subentry_id` attributes
* Schedule the LED switch's reconnect state restore as a background task instead of one Home Assistant would wait on during shutdown
* Add a focused automated test suite (42 tests) covering this release's core logic
* Fix a real `mypy --strict` failure in the device-registry compatibility helper: its forward-looking `async_update_device(new_config_entry_id=...)` call (for the single-call move added in Home Assistant 2026.8) is only ever reached once `inspect.signature()` confirms the installed release actually has those parameters, but mypy checks the call against whichever release happens to be installed - a documented `type: ignore[call-arg]` now covers that on any older release, without changing the runtime logic
* Fix the remaining `mypy --strict` findings in the test suite - none affected runtime behavior: reading the test double's recorded writes now goes through one typed helper instead of per-line `type: ignore` comments, `ConfigSubentry.data` is built as a real `MappingProxyType`, and a few `monkeypatch`-installed mocks are now asserted on through their own variable instead of through the patched attribute
* Fix a real regression found during an independent line-by-line audit: recalibrating an already-configured blind reloaded the *entire* hub (disconnecting the serial port and rebuilding every cover, sensor, and switch on it) immediately after the calibration-complete signal had already updated the live entity in place, silently undoing that live update. The entry-update listener now ignores exactly the three fields (`open_time`, `close_time`, `last_calibration`) the live signal already handles; every other subentry change - a new/removed blind, a re-paired device ID, a changed status identity - still reloads as before, since those genuinely need it. Covered by a new regression test
* Remove the leftover `pair` service description from `strings.json` and all four translations: no such service has been registered since `services.yaml` dropped it, only `test_command` exists
* Remove unreachable translation keys left over from before blinds moved to config subentries (`config.step.menu`, `config.abort.no_hub`, the top-level `config.abort.reconfigure_successful`)
* Sync `pyproject.toml`'s version with `manifest.json`
* Update the device-registry compatibility module's docstring: `async_get_device_by_identifier` is no longer described as a hypothetical future addition - it has been a stable, released method since Home Assistant Core 2026.9, confirmed against current Home Assistant source. The fallback path for releases without it (this integration's declared minimum is 2025.3.0, per `hacs.json`) is unchanged
* Bump the pinned test toolchain to match current Home Assistant: `pytest-homeassistant-custom-component` 0.13.299 → 0.13.367, with `requires-python` and `[tool.mypy] python_version` raised to 3.14 to match. This is the dev/CI floor only - the integration's own minimum supported Home Assistant version in `hacs.json` is unchanged, so installations on older Core releases are not affected
* Fix the package name typo in `pyproject.toml` (`schellenber_usb` → `schellenberg_usb`, matching the actual `schellenberg_usb` domain)
* Remove the six stray `.patch` files from the repository root - development artifacts that were never part of the shipped integration
* Simplify the README's description of the "stick busy" log message: drop the now-unneeded mention of filtering, since debug-level logging during normal operation already covers it (added in v1.0.3, see above)
* Add mock-test coverage for the rest of the configuration and options user interface, previously untested: `test_config_flow.py` (the entire pairing, manual-entry, status-discovery, reconfigure, and Developer Tools subentry flow - by far the largest and previously the only completely uncovered part of this integration), `test_options_flow.py` (the hub's serial-port options flow), `test_options_flow_calibration.py` (the shared calibration step machinery), and `test_sensor.py`. All are driven through Home Assistant's real flow managers (`hass.config_entries.flow`/`.subentries`/`.options`) rather than hand-mocked flow classes. The suite grows from 43 to 95 tests in v1.0.4 itself; see above for this variant's own count
